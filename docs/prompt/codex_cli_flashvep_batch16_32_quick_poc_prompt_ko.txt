당신은 Qwen3-VL-30B-A3B-Instruct MoE EP 연구 코드베이스에서 FlashVEP Quick PoC를 수행합니다.

상세 스펙:

    docs/flashvep_batch16_32_quick_poc_spec.md

이 문서를 처음부터 끝까지 읽고 그대로 수행하세요.

이번 작업의 목적은 복잡한 tile simulator를 구현하는 것이 아니라, 기존 Phase 1b의 TP2/DP2/EP4 경로에서 **global batch 16과 32를 사용했을 때 local expert latency와 expert fraction이 실제로 커지는지 빠르게 확인하는 것**입니다.

# 고정 조건

- Physical GPU는 반드시 `4,5,6,7`만 사용
- TP=2, DP=2, EP=4, PP=1
- 기존 Phase 1b와 동일한 Qwen3-VL-30B-A3B-Instruct local snapshot
- BF16
- 동일한 896×896 gray image
- 동일 prompt
- prefix caching off
- `max_tokens=1`
- Batch는 `16`, `32`만 측정
- Batch 16을 먼저 실행
- Batch 32가 OOM이면 한 번만 실패를 기록하고 추가 우회 없이 중단

# 실험 프로토콜

각 batch:

    warmup = 3
    iterations = 8

실행 시간이 너무 길면:

    warmup = 2
    iterations = 5

까지 줄일 수 있습니다. 변경 사실을 보고하세요.

Batch 내 요청은 동일한 image/prompt를 복제합니다.

반드시 기록:

- actual global batch
- real requests per DP rank
- total prompt tokens
- total routed assignments
- rank별 local assignments
- max local expert batch
- output token consistency
- profiler overhead

# 즉시 중단 조건

다음이면 중단하세요.

- GPU 4,5,6,7 외 GPU가 필요함
- Batch 16 OOM
- Batch 32 OOM: Batch 16 결과는 유지하고 Batch 32는 추가 우회하지 않음
- DPEP path가 유지되지 않음
- Batch 요청이 실제 동시 batch가 아니라 순차 요청으로 실행됨
- DP rank 중 하나에만 요청이 집중됨
- profiler overhead >20%
- 기존 artifact를 덮어써야 함

# 판정

## GO

Batch 16 또는 32에서 모두 또는 대표적으로 다음을 만족할 때:

- `T_expert_max >= 1.0 ms`
- expert fraction >=25%
- communication-to-expert ratio가 Batch 1보다 감소
- 기존 또는 extended optimistic oracle >=1.15x
- 최소 2/3 selected layer에서 반복
- profiler uncertainty보다 gain이 큼

## HOLD

- expert fraction 20~25%
- oracle 1.10~1.15x
- Batch 32에서만 개선
- backend/profiler 불확실성이 큼

## NO-GO

- Batch 16/32에서도 expert <1.0 ms
- expert fraction <20%
- dispatch/combine이 expert보다 더 빠르게 증가
- 모든 대표 layer oracle <1.10x
- communication 병목이 계속 지배
