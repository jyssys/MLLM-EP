# 이번 작업의 목적

vLLM serving scheduler를 수정하거나 end-to-end 시스템을 구현하는 것이 아닙니다.

실제 Qwen3-VL vision-heavy MoE workload를 scheduler-free offline replay하여, 길어진 expert execution을 중심으로 다음 overlap이 실제 throughput을 개선하는지만 확인합니다.

```text
Dispatch(next microbatch) || Expert(current microbatch)
Combine(previous microbatch) || Expert(current microbatch)
```

Expert execution이 반드시 핵심 overlap window입니다.

# Phase O1 — Compute-bound crossover

Batch-equivalent workload:

```text
B_eq = 16, 32, 64, 128
```

각 workload에서 반드시 기록:

- real/vision tokens
- total routed assignments
- rank별 assignments
- critical-rank assignments
- max local-expert batch
- dispatch
- expert max
- combine
- full MoE
- expert fraction
- communication/expert
- tokens/s
- assignments/s

Request batch 숫자만 보고하지 말고 실제 routed workload를 함께 보고하세요.

Capture를 반복하여 workload를 키우면 synthetic scaling임을 명시하세요.

# Phase O2 — Expert-centered wavefront

O1 결과에서 compute-bound representative workload 2개만 선택하세요.

각 workload:

```text
K = 2, 4 microbatches
```

비교:

1. full-batch serial
2. microbatch serial
3. expert-centered wavefront

필수 wavefront:

```text
D0
E0 || D1
E1 || C0 || D2
E2 || C1 || D3
E3 || C2
C3
```

Dispatch와 combine이 같은 NCCL resource에서 동시에 진행 불가능하면 통신끼리는 serialize하고 expert와만 overlap하세요.

CUDA event dependency를 명시적으로 사용하세요.

모든 rank의 collective order는 동일해야 합니다.

# Attention/Router 확장

필수 O2가 actual speedup `>=1.10x`일 때만 선택적으로 수행할 수 있습니다.

```text
Expert(i) || Attention/Router/Dispatch(i+1)
```

Attention과 expert가 모두 느려지면 즉시 중단하세요.

선택적 확장은 필수 결과가 아닙니다.

# Gate

## GO

- correctness 통과
- 대표 workload 하나에서 actual speedup `>=1.15x`
- 다른 workload에서 `>=1.10x`
- actual D/E 또는 E/C overlap 확인
- fragmentation penalty `<15%`
- gain이 profiler uncertainty보다 큼

## HOLD

- speedup `1.05x~1.15x`
- backend/collective assumption에 민감
- Attention/Expert contention에 따라 결론 변동

## NO-GO

- compute-bound에서도 `<1.05x`
- fragmentation/collective 반복이 이득 제거
- 실제 overlap 없음
- correctness 실패
- custom kernel 없이는 진행 불가능
