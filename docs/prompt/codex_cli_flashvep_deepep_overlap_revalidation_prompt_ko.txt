## 가장 중요한 목표

다음 질문에 실제 측정으로 답하라.

1. 기존 1.034x 결과는 일반 AllGather/ReduceScatter implementation의 contention 때문이었는가?
2. DeepEP를 쓰면 overlap 시 Dispatch slowdown을 기존 +258.5%에서 크게 줄일 수 있는가?
3. DeepEP serial 대비 DeepEP overlap은 B64/B128에서 실제 speedup을 만드는가?
4. stock vLLM `deepep_high_throughput` + DBO는 Qwen3-VL vision-heavy prefill에서 end-to-end 이득이 있는가?
5. stock DeepEP/DBO 위에 향후 vision-straggler-aware FlashVEP adaptation을 추가할 여지가 남는가?

## 연구 경계

DeepEP는 이번 연구의 novelty가 아니다. DeepEP는 고성능 communication substrate다.

이번 PoC에서는 다음 세 효과를 반드시 분리하라.

- AG/RS serial → DeepEP serial: backend 자체 이득
- DeepEP DBO off → DeepEP DBO on: stock overlap 이득
- 향후 stock DBO → FlashVEP: 이번에는 구현하지 않을 adaptation 영역

DeepEP나 DBO의 이득을 FlashVEP 성능으로 잘못 보고하지 마라.

- 기존 사용자 변경 사항이 있으면 보존하고 상태를 보고하라.

### Phase 1 — DeepEP 설치와 smoke

- 별도 환경 생성
- pinned DeepEP build/install
- 4-rank intranode initialization
- BF16, hidden=2048, top-k=8, experts=128, EP4 dispatch/combine correctness
- DeepEP import path와 commit 기록
- backend kernel이 실제로 실행됐음을 확인

설치 실패 시 무한히 patch하지 말고 원인, 시도, 정확한 오류를 BLOCKED 보고서에 남겨라.

### Phase 2 — stock vLLM backend matrix

동일 모델·동일 입력·동일 topology로 다음을 비교하라.

A.
- `allgather_reducescatter`
- DBO off

B.
- `deepep_high_throughput`
- DBO off

C.
- `deepep_high_throughput`
- DBO on

Controlled request:

- 896×896 controlled image
- exact prompt: `Describe this image briefly.`
- processor가 생성한 token 수를 다시 기록
- request count: 가능한 범위에서 1, 4, 8, 16
- warmup ≥5
- measured repetitions ≥20

측정:

- request wall
- prefill/TTFT
- tokens/s
- memory peak
- correctness output
- actual selected backend
- DBO activation proof
- per-rank route load 가능 시 기록

비교:

- A→B는 DeepEP backend 효과
- B→C는 stock overlap 효과
- A→C는 전체 substrate 효과

### Phase 3 — operator-level DeepEP replay

기존 layer-24 capture를 우선 재사용하라.

필수 workload:

- B_eq=32
- B_eq=64
- B_eq=128

비교:

1. Existing AG/RS serial
2. Existing AG/RS wavefront K=2
3. DeepEP serial
4. DeepEP overlap K=2
5. K=4는 fragmentation이 허용될 때만
6. DeepEP가 공식적으로 지원하는 communication-SM 설정 sweep

각 설정에서 다음을 측정하라.

- D alone
- E alone
- C alone
- D||E
- E||C
- D||E||C wavefront
- D/E/C serial sum
- D/E/C overlap sum
- stage slowdown ratios
- wall speedup
- overlap fraction
- memory peak
- all-rank correctness

DeepEP V1이 static SM 설정만 허용하면 process별로 별도 실행하라. 임의 값을 강제로 kernel에 넣지 마라.

### Phase 4 — Nsight

best DeepEP overlap 1개와 대응 serial 1개만 Nsight Systems로 수집하라.

확인:

- DeepEP communication kernel과 Triton expert kernel의 실제 concurrent residency
- stream dependency
- CPU sync/gap
- communication duration
- Expert duration
- repeated kernel launch

`.nsys-rep`는 commit하지 말고 작은 exported summary와 명령어만 commit하라.

## correctness 기준

DeepEP serial을 reference로 사용하라.

- `torch.testing.assert_close`
- max abs
- mean abs
- cosine similarity
- top-k IDs/weights preservation
- source token order restoration
- all ranks PASS

BF16 accumulation order 차이를 고려한 tolerance를 명시하라. Bitwise equality를 근거 없이 요구하지 마라.

## Gate

### GO

다음을 모두 만족:

- DeepEP correctness PASS
- actual DeepEP backend proof
- Nsight actual overlap
- E slowdown ≤1.05x
- D slowdown ≤1.25x
- B64 또는 B128 중 하나에서 DeepEP serial 대비 ≥1.15x
- 다른 workload에서 ≥1.10x
- stock DBO의 end-to-end 이득
- workload별 차이가 있어 adaptive FlashVEP 여지가 존재

### HOLD

- 최고 1.05x~1.15x
- operator 이득이 end-to-end에서 줄어듦
- contention은 감소했으나 stock DBO가 작음
- 원인이 명확하고 후속 debate 가치가 있음

### NO-GO

- optimized DeepEP에서도 최고 <1.05x
- actual overlap 없음
- severe contention 지속
- integration overhead가 이득보다 큼
- stock DBO가 모든 이득을 가져가고 adaptation 여지가 없음
- correctness 실패

### BLOCKED

설치/환경 문제로 핵심 실험을 실행하지 못함. BLOCKED를 NO-GO로 쓰지 마라.
