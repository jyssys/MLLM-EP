# Part A — `0.447 ms` expert time의 의미 검증

이전 결과의 `T_expert_max = 0.447 ms`를 그대로 믿거나 비정상이라고 단정하지 마세요. 다음을 조사하세요.

## A1. Timing scope 확인

기존 instrumentation 코드를 읽고 `expert` 범위가 정확히 무엇을 포함하는지 확인하세요.

- local fused/grouped expert GEMM만 포함하는가?
- token gather/prepare를 포함하는가?
- routing top-k를 포함하는가?
- local finalize/scatter를 포함하는가?
- combine collective를 포함하는가?
- 비동기 CUDA launch만 측정하고 실제 완료를 놓치지는 않는가?
- 시작과 종료 CUDA event가 같은 stream에 기록되는가?
- `T_expert_max`는 rank별 duration의 max인가, expert별 kernel의 max인가?
- complete fused MoE call 1.057 ms와 어떤 관계인가?

이를 `phase1b_expert_timing_audit.md`에 명확히 설명하세요.

## A2. Workload shape 확인

대표적인 vision-heavy request와 selected layer에서 다음을 기록하세요.

- total tokens
- visual/text tokens
- top-k
- 전체 routed assignments
- rank별 실제 local routed assignments
- local expert별 token counts
- 가장 큰 local expert batch
- expert kernel input/output dtype와 shape
- 사용 backend와 kernel 이름
- 각 rank가 실제로 소유하는 expert 수

라우팅 tensor 전체가 모든 rank에 복제되어 있어도 그것을 실제 local expert workload로 오인하지 마세요.

## A3. 독립적인 local expert microbenchmark

가능하면 실제 실행에서 대표 layer의 local expert input, routing/local assignment shape만 캡처하여 동일 backend의 local expert call을 별도로 replay하세요.

조건:

- model output 경로는 변경하지 않음
- capture는 opt-in
- warm-up 충분히 수행
- CUDA event로 최소 100회 측정
- median, p10, p90, mean, stddev 보고
- full-batch shape와 실제 local shape를 구분
- capture tensor가 지나치게 크면 selected layer 하나만 사용
- 파일에 model weight 자체를 저장하지 않음

microbenchmark가 기존 0.447 ms와 유사한지 확인하세요.

## A4. 대략적인 FLOP sanity check

Qwen3-VL MoE config에서 실제 hidden size, expert intermediate size, top-k를 읽어 다음을 계산하세요.

SwiGLU expert의 routed assignment 하나에 대해 gate/up/down projection의 근사 FLOPs:

    FLOPs_per_assignment ≈ 6 * hidden_size * expert_intermediate_size

rank별 실제 local assignment 수를 사용해:

    estimated_local_expert_FLOPs
    achieved_TFLOP/s = FLOPs / measured_time

를 계산하세요.

이 값이 H100에서 물리적으로 가능한지, 지나치게 낮거나 높은지 해석하세요.
이는 대략적인 sanity check이며 정확한 kernel instruction count라고 주장하지 마세요.

## A5. 결론

다음 중 하나로 결론을 내리세요.

- `0.447 ms is plausible and correctly scoped`
- `0.447 ms is plausible but measures only pure local GEMM`
- `0.447 ms is biased by instrumentation`
- `0.447 ms is incorrectly scoped or asynchronously measured`
- `inconclusive`

근거를 함께 제시하세요.

# Part B — 실제 DPEP Phase 1b 구성

## B1. Smoke test

먼저 TP2/DP2/EP4 후보 구성으로 가장 작은 smoke test를 수행하세요.

확인:

- 네 GPU worker가 모두 정상 시작
- 동일 checkpoint 사용
- output token과 기본 결과 기록
- 실제 parallel state 기록
- rank별 expert ownership 기록
- runtime prepare/finalize class 기록
- 실제 dispatch 및 combine collective 존재 여부
- collective backend와 kernel 이름
- 각 rank가 request에 어떻게 참여하는지

FlashInfer CUTLASS가 다시 멈추면:

1. hang reproducer와 마지막 진행 지점을 기록
2. 관련 없는 GPU process를 kill하지 않음
3. 기존과 동일하게 Triton fallback을 사용할 수 있으나 backend substitution임을 명시
4. fallback path에서도 실제 DPEP collective가 존재하는지 재확인

## B2. 즉시 중단 조건

다음 중 하나이면 상세 profiling으로 넘어가지 말고 중단하세요.

- 실제 dispatch collective가 없음
- combine이 여전히 TP-only all-reduce이며 DPEP combine이 없음
- 네 rank가 실제 expert-parallel request 처리에 참여하지 않음
- 단일 요청 의미가 기존과 비교 불가능하게 변경됨
- baseline이 안정적으로 완료되지 않음

이 경우 원인과 재현 명령을 기록하고 Phase 1b NO-GO로 종료하세요.

# Phase 1b Gate

FlashVEP Phase 2 진행을 권장하려면 모두 만족해야 합니다.

1. 실제 dispatch 및 combine EP collective가 확인됨
2. internally consistent oracle speedup median >= 1.15x
3. representative selected layer 여러 개에서 반복적으로 >= 1.15x 또는 전체 prefill 기준 >= 1.15x
4. profiler overhead로 설명되지 않는 headroom
5. expert fragmentation/producer-consumer 구조상 tile streaming 가능성이 존재
6. 현재 strong baseline이 이미 대부분 overlap하고 있지 않음

다음의 경우 최종 NO-GO로 결론 내리세요.

- median oracle < 1.10x
- dispatch가 너무 작거나 없음
- expert window가 매우 짧고 combine tail이 지배적
- 이득이 특정 layer 하나에만 존재
- profiler noise가 예상 이득보다 큼

1.10x~1.15x 사이는 HOLD로 두고 Phase 2를 자동 진행하지 마세요.
