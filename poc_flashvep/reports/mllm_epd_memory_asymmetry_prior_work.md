# MLLM EPD 메모리 비대칭성과 캐싱 선행연구

## 신규성 판정

**Embedding과 LM Prefix KV를 함께 캐싱하는 발상과 공통 메모리 풀은 선행연구에 이미 있다.** ElasticMM §3.3은 이미지 해시 기반 임베딩과 최장 일치 멀티모달 Prefix KV를 각각 LRU 풀로 관리한다. VisMemo §3.4.3은 SGLang과 Mooncake의 중복 저장을 줄이기 위해 임베딩과 KV를 실제 하나의 가변 크기 메모리 풀에 넣고 배치, 퇴거 및 SSD→DRAM 승격을 함께 관리한다. Mooncake의 EPD RFC도 공유 Visual Feature 및 Text/Multimodal KV 저장소와 중단 상태 복원을 제안한다. [ElasticMM §3.3](https://arxiv.org/html/2507.10069v3#S3.SS3) · [VisMemo §3.4.3](https://arxiv.org/html/2610.25136) · [Mooncake EPD RFC](https://github.com/kvcache-ai/Mooncake/issues/2750)

검증할 차이는 **고정 1E/1P/1D에서 E의 안전한 VRAM을 정확한 요청 경계 캐시에 배정하고, 이미지 단위 재사용과 문맥 종속 Prefix 재사용의 차이가 동일 바이트 예산의 Generic Cost-aware Policy보다 실제 Goodput을 개선하는지**다. VisMemo의 공통 풀은 GPU의 로컬 L1과 별개인 백엔드 DRAM을 CUDA에 등록하고 SSD를 연계하는 구조이며, 근사 이미지 패치 재사용 경로도 포함한다. ModServe는 E의 낮은 메모리 활용도를 이미 지적하고 E와 Decode의 배치를 연구했다. 전용 E 티어가 유리한지는 기존 3GPU E/P Colocation, 호스트 캐시, P 또는 D에 같은 용량을 둔 구성과 비교해야 한다. [VisMemo §3.3–3.4, Fig. 11](https://arxiv.org/html/2610.25136) · [ModServe §6.4](https://arxiv.org/html/2502.00937v1#S6.SS4)

이 문서의 `CODE_AUDIT`는 공개 소스 또는 로컬 설치 코드를 직접 읽은 항목, `PAPER`는 원문 방법 확인, `DOC`는 공식 구현 문서 확인, `RFC`는 제안 단계다. 다른 팀의 결과는 이번 H200 캠페인의 `MEASURED_ONLINE` 또는 `MEASURED_PHYSICAL` 실측에 합산하지 않는다.

## 여섯 가지 중복 질문에 대한 답

1. **E VRAM을 KV 저장소로 사용한 선례가 있는가?** 프로젝트의 EADA는 E에 Decode KV를 보관하고 매 Decode Step에서 사용했다. ModServe의 E+Decode Colocation도 E에 D 상태를 둔다. 조사한 원문 및 공개 구현에서 Exact 전용 E-VRAM 경계 저장소의 동일 CPU/GPU 예산 정책까지 검증한 결과는 확인하지 못했다. [프로젝트 EADA 보고서](https://github.com/jyssys/MLLM-EP/blob/07892cbe7193366ec422f1df82006c6e69f91cec/poc_flashvep/reports/mllm_encoder_assisted_decode_attention_final_summary.md) · [ModServe §6.4](https://arxiv.org/html/2502.00937v1#S6.SS4)
2. **Embedding 및 Prefix KV가 예산을 공유하는가?** VisMemo에서 백엔드 DRAM 풀을 공유하며, ElasticMM 원문과 LMCache Legacy EC는 두 Pool을 별도로 관리한다. [VisMemo §3.4.3](https://arxiv.org/html/2610.25136) · [ElasticMM §3.3](https://arxiv.org/html/2507.10069v3#S3.SS3) · [LMCache EC](https://docs.lmcache.ai/non_kv_cache/encoder_cache.html)
3. **P→D 대기 중인 KV를 E가 보관했는가?** MemServe와 HydraInfer는 일반 Pending/Live State 이동 및 Target 예약에 가까운 선례다. 살펴본 소스에서 P 완료 후 D Admission을 기다리는 동안 Dedicated E가 임시 보관하는 동일 경로의 구현은 확인하지 못했다. P에서 실제 대기 KV를 반환해 이후 Prefill이 앞당겨지는 계측이 필요하다. [MemServe](https://arxiv.org/html/2406.17565) · [HydraInfer](https://arxiv.org/html/2505.12658v1)
4. **GPU Pooling을 EPD에 적용했는가?** HydraInfer는 EPD의 이미지/LM 상태에 공통 Paged 추상화와 전송을 적용하며, Mooncake RFC는 EPD Feature/KV 공유를 제안한다. E 배치를 별도로 확인해야 한다. [HydraInfer §4](https://arxiv.org/html/2505.12658v1) · [Mooncake RFC](https://github.com/kvcache-ai/Mooncake/issues/2750)
5. **Modality-aware Admission과 Eviction 선례가 있는가?** VisMemo는 Exact와 근사 재사용 종류에 따라 적재와 보호 정책을 바꾼다. 이번 Exact-only 후보는 동일 Storage Budget과 같은 Tier를 가진 Label-blind Cost-aware Policy 이상의 효과를 보여야 한다. [VisMemo §3.4](https://arxiv.org/html/2610.25136)
6. **Raw Image, Embedding, KV를 함께 고려했는가?** ElasticMM의 공개 입력 전송 캐시와 논문의 두 계산 결과 재사용 경로가 서로 다른 표현을 다룬다. 조사한 고정 코드에서 세 가지를 같은 E-VRAM 바이트 예산으로 함께 퇴거하는 구현은 확인하지 못했다. 세 표현을 지원한다는 사실만으로 성능 기여를 판단하기 어렵고, 실제 동일 예산의 검증이 필요하다. [ElasticMM 입력 Cache 구현](https://github.com/hpdps-group/ElasticMM/blob/dc0132629baae0dd6914816b58f3d5cf426d416d/elasticmm/cache/multimodal_cache.py) · [ElasticMM 원문](https://arxiv.org/html/2507.10069v3)

## 비교 설계에 미치는 영향

- **B/C 먼저**는 기존 Cache를 모두 활성화한 EPD에서 Encode 호출 수와 APC hit-token 수를 독립적으로 수집한다. 같은 Dataset, Model, Warmup에서 E가 GPU Embedding Hit를 처리하는 구성과 P가 CPU Embedding Hit로 E를 건너뛰는 구성을 비교한다. 이미지 재정렬 또는 새 질문으로 앞선 Prefix가 바뀌면 Embedding과 KV의 키를 각각 확인한다.
- **공통 예산 검증**은 Native EC+APC, Embedding-only, KV-only, 최강 Static Split 및 같은 Candidate/Transfer/Admission 비용을 사용하는 Generic Cost-aware Cache를 포함한다. Pool이 배치된 E/P/D와 추가로 할당한 물리 GiB를 분리해 기록한다. 중첩된 계산 절약량은 실제로 생략한 E/P Stage를 기준으로 요청당 한 번 기록한다.
- **A/D 기준선**은 P의 완료 KV 고정 바이트·수명, 실제 P Backpressure와 D Preemption 빈도가 확인된 경우 활성화한다. P→D 직접 전송 및 P/CPU Pending Buffer를 포함하고 Source Pin/ACK와 E→D 복원 완료까지 비용을 기록한다. D의 Compute 병목과 KV Admission 병목을 별도 지표로 남긴다.
- **E 판정 범위**는 실제 다중 모델 Arrival과 전환 트레이스가 없으면 Weight Copy 가능성과 전송 비용으로 한정한다. 단일 모델의 Prompt Cache 개선과 합산하지 않는다.
- **성능 판정**은 이 문서의 구조 및 코드 근거와 별개다. 동일 GPU 수·Cache Bytes의 전체 Arrival Trace에서 Encoder·P/D 간섭, TTFT, ITL, TPOT, Goodput, 정확성을 함께 평가해야 한다. 최강 Generic과 차이가 없을 경우 독립적인 Modality 정책 근거는 미확정이다.
