# LongBench400 Pipeline-load Reference Audit

작성일: 2026-11-21 KST.
이 문서는 Load Reference와 실제 Capacity의 차이를 기록한다.
기존 측정, SLO, Request 또는 동결한 Config를 변경하지 않는다.

## 두 가지 Rate

기존 C0 Discovery는 Serial P+D Service로 Reference Rate를 계산했다.
P와 D는 Online Pipeline에서 서로 다른 Request를 동시에 처리할 수 있다.
따라서 Serial Rate를 실제 Pipeline Capacity로 사용할 수 없다.

새 Supplement의 Reference는 다음 식을 사용한다.

`Estimated Pipeline Rate = 1000 / max(mean P service ms, mean D whole-request service ms)`

P Service는 P Submit→Ready의 Host 구간이다.
D Whole-request Service는 D Submit→Finish의 Host 구간이다.
두 구간은 Transfer, Host Work 및 Scheduling을 포함한다.
GPU-exclusive 시간이 아니다.
위 식도 Sustainable Capacity의 실측값이 아니다.
실제 Queue, Achieved Rate 및 Drain을 함께 확인해야 한다.

## 기존 Matrix의 범위

기존 64-Cell Confirmation은 Input Bucket 안에서 Output별 QPS를 같게 유지했다.
Output8/16의 일부 조건은 실제 Pipeline 처리율보다 매우 낮은 부하였다.
Output64/128은 D Decode Residency가 길다.
같은 QPS라도 이 조건은 Knee 또는 Overload에 가까울 수 있다.
따라서 기존 Matrix 전체를 Low-load라고 부르지 않는다.

새 `proper_pipeline_load_discovery_frozen_v1.json`의 Qualifier에는 `light-load confirmation`이라는 표현이 있다.
이는 일부 Short-output Cell에만 해당한다.
전체 64개 Cell의 Load Class를 의미하지 않는다.
동결한 파일은 그대로 보존한다.
이 문서가 해당 표현의 범위를 제한한다.

## 새 Discriminating Design

3K–6K와 20K–36K의 실제 Discovery Prompt를 사용한다.
Output8에서는 Estimated Pipeline Rate의 0.75/1.00/1.15배를 검사한다.
각 Cell에서 Native, Layer2/4/8/12, Token2/4/8/12, Hybrid4/Suffix≈L/8을 실행한다.
Axis 사이의 Prompt와 Arrival Trace는 같다.
실제 Batch는 1/1/1이며 Source Credit은 4다.

Output16/64를 같은 절대 QPS로 실행하는 Counterfactual도 포함한다.
Output64는 자체 Estimated Rate의 Control도 포함한다.
Severe Overload Control을 정상 Sustainable Serving으로 표시하지 않는다.
불리한 Output 또는 Cut의 결과도 삭제하지 않는다.

3K–6K는 원래 Prompt 32개를 사용한다.
20K–36K의 33개 Discovery Pool에는 Exact-work 32개 조합이 없었다.
같은 사전 산술 조건을 만족하는 30개 조합을 사용한다.
원문을 Padding하거나 Request를 복제하지 않았다.
두 Input Stratum의 N 차이를 기록한다.
각 Cell 내부에서는 모든 방법의 N이 같다.

선정 산술 조건은 Input Token 합의 1,152 Divisibility다.
이를 사용해 Pure Axis와 Hybrid의 Aggregate Rows를 정확히 맞춘다.
선정에 Serving Latency 또는 승패 결과를 사용하지 않았다.
두 Bucket에서 선택한 Length 분포와 N은 별도로 보존한다.

## 판정 제한

이 Supplement는 독립 Start 1회의 Discovery다.
한 Start의 Request를 독립 Start로 취급하지 않는다.
새 Winner 후보는 새로운 Request와 Arrival Seed에서 반복해야 한다.
Native-relative ITL p99와 TPOT p95의 5% CI Gate도 유지한다.

실제 Queue Growth는 유한 Trace의 관측값이다.
Queue가 마지막에 0이 됐다는 이유만으로 Stable Capacity를 주장하지 않는다.
모든 유한 Trace는 Arrival이 멈춘 후 Drain할 수 있다.
Measured Completion Rate와 Offered QPS도 구분한다.

Achieved req/s는 전체 측정 Window의 완료 Request 수를 사용한다.
Offered QPS와 같은 값이 아니다. 모든 요청의 Drain 시간을 포함한다.
Coordinator의 Pipeline Waiting은 Worker 내부 Queue나 GPU Idle과도 다르다.
Source Credit과 Whole-request C0 D Guard가 이 Protocol의 일부다.
따라서 이 결과를 C3 Continuous Native 또는 C3 Hybrid의 Capacity로 재사용하지 않는다.
