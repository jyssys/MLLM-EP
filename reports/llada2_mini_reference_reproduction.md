# LLaDA2.0-mini reference quality reproduction (Phase 1 only)

This report uses the [Phase-1 reproduction contract](/home/esjung/MLLM-EP-github/poc_flashvep/reports/llada2_reproduction_true_ep_poc_spec.md), with the user's explicit restriction to stop before any EP profiling or optimization. The work is in an isolated clean worktree; old Flash experiments and the dirty original tree were not changed.

## Source of truth and environment

The pinned checkpoint is [`inclusionAI/LLaDA2.0-mini`](https://huggingface.co/inclusionAI/LLaDA2.0-mini) revision `dad945cac317da394b390f82c7b40691d8a881ed`, with the tokenizer and remote `modeling_llada2_moe.py` from the same snapshot. Its downloaded config states a 20-layer BF16 MoE, hidden size 2048, 256 experts, top-k 8 and one shared expert. This is **not** the previous 100B Flash checkpoint. The reference generation is the checkpoint's unmodified `model.generate` via Hugging Face `AutoModelForCausalLM` and its own `apply_chat_template`.

The model card example actually passes `steps=32`, `block_length=32`, `gen_length=512`, `temperature=0`, with `eos_early_stop=True`; the [official LLaDA2.0 paper](https://arxiv.org/pdf/2512.15745) also states `temperature=0`, B32 and decoding threshold `0.95` for its evaluated models. Our quality anchor therefore uses the spec's threshold `0.95`. The custom source treats `steps` as a **maximum per generated block**, not a sequence-wide NFE budget. `minimal_topk` limits the decoder's maximum transfer schedule and does not mean top-k expert routing. Actual NFE here counts `model.forward` calls observationally, without changing input/tensors/output. All GPU execution is single-GPU reference generation on physical H100s 4–7; four independent workers may evaluate disjoint IDs, but no TP or EP is used. The full exact environment is recorded in `artifacts/reproduction/environment.txt`.

There is a source-level reference inconsistency: the Mini `generate` docstring calls `temperature=0` greedy, but `_sample_with_temperature_topk_topp` skips temperature scaling and **always** calls `torch.multinomial` on softmax probabilities. This PoC does not patch that algorithm. Each public sample uses a fixed per-ID RNG seed for repeatability; a published evaluation using an actual greedy dInfer `do_sample: false` path may differ even when the nominal temperature matches.

The GSM8K reference prompt is the official [dInfer Mini evaluation YAML](https://github.com/inclusionAI/dInfer/blob/master/evaluations/tasks/gsm8k/gsm8k-llada-mini.yaml): `Question: ...\nLet's think step by step\nAnswer:` with its fixed four examples. The checked-out dInfer revision is `1ffeb961cd258bede74fcf5ca8a416ae6d57b18f`; its Mini evaluation shell passes `--apply_chat_template` and `gen_length=2048`, but defaults to threshold `0.80` under a different dInfer/TP4 decoder. That shell is therefore a prompt/length reference, **not** an exact score-matched HF generation protocol. This changes prompt protocol compared with the old raw-question Flash benchmark, so raw cross-model scores are not a controlled checkpoint-only contrast. The benchmark answer parser is independently validated below. No threshold sweep is done in Phase 1.

## Generation sanity

Ten official Mini generations covered arithmetic, multi-step arithmetic, a syllogism, a simple explanation and a general instruction. All ten were nonempty, had no remaining MASK token and ended by EOS. All arithmetic answers were coherent and numerically correct. The measured forward count ranged 5–110. Four of ten *returned tensors* contained the full formatted prompt before the answer. Source inspection identified the exact reason: the official `eos_early_stop` branch returns `final_x` **including the prompt**, while the ordinary exit returns only generated IDs. This is a postprocessing boundary bug, not evidence that the model actually generated the prompt again. The evaluation wrapper now detects the input-ID prefix and strips it **after** the unchanged official generation; three CPU regression probes passed. The preliminary sanity artifact preserves the raw unnormalized return for diagnosis. Its old `generation_tokens` count can overstate true generated tokens for early-EOS cases; all staged benchmark files with `normalized` in the name use the corrected output boundary.

The exact same ten seeded sanity prompts were rerun after output normalization. All ten again terminated by EOS without empty output or remaining MASK; the corrected true generated lengths are 11–189 tokens, and the same four early-EOS prompt-prefix flags are preserved. `artifacts/reproduction/sanity_samples_normalized.jsonl` is the authoritative sanity record; the earlier `sanity_samples.jsonl` is retained only as a pre-fix diagnostic artifact.

## GSM8K staged result

Stage A used the fixed first 32 GSM8K test IDs with the official Mini four-shot prompt, B32/steps32/threshold0.95/temp0, and `gen_length=512`. The last-number/final-cue parser scored **29/32 = 90.625%** (Wilson 95% CI 75.78–96.76%). There were 30 EOS exits, two length-cap exits, zero remaining MASKs, zero empty outputs, mean/median NFE 95.03/69 and mean/median generated lengths 191.28/162.5. These outputs are structurally normal and justify Stage B. One length-cap output explicitly says the correct answer `18` *before* a truncated verification that ends with `5`; the fallback last-number parser scored it false. The manually visible score is at least 30/32, but no human-adjusted full accuracy is claimed before the required parser audit. A second length-cap case stops before calculating its answer; one fully terminated case gives a genuinely wrong arithmetic result.

All 32 Stage-A outputs were also visually audited against the final answer and ground truth. This gives 30/32 human-visible correct; of the two human-visible errors, one is unfinished at the cap and one is a terminated arithmetic mistake. The third parser error is the truncated *verification after an already-correct answer* described above. The machine summary and every per-sample prompt, output, parser, manual answer, NFE and termination flag are in `artifacts/reproduction/gsm8k_stage32_*` and `parser_review_first32.csv`. This healthy gate authorized the same fixed first 128 IDs and, subsequently, the completed full cohorts. No threshold sweep, EP optimization or Phase-2 profiling was started.

The first 50 fixed test IDs have now each been manually checked from the visible answer text (including the failing/truncated outputs). Raw parser score was 45/50 = 90%; human-visible score was **46/50 = 92%**. Manual failure taxonomy: two `TRUNCATED` without a final answer, two `MODEL_WRONG`, and one `PARSER_WRONG` where a valid correct answer was followed by truncated verification. Thus parser failure is real but, in this small fixed cohort, only one of five scored failures; it cannot alone explain the prior Flash 10.92%. The cap-512 per-sample triage is `artifacts/reproduction/gsm8k_stage128_parser_validation.csv` with manual flags, and the explicit review decisions are `parser_review_first50.csv`. The required `parser_validation.csv` now holds the final cap-2048 50-row audit instead.

Stage B completed all first 128 fixed test IDs at the same `gen_length=512`. Raw parser accuracy was **115/128 = 89.844%** (Wilson 95% CI 83.40–93.97%); 123 exited at EOS and five at the length cap; there were zero remaining MASKs or empty generations. Mean/median NFE was 90.91/73, and mean/median generated length was 177.73/155. The published 94.24% is marginally above this finite-sample parser CI, but a 50-sample manual review shows a real parser false negative, five outputs are length-capped, and the nominal `temperature=0` source samples despite its greedy documentation. No one mechanism is proven to explain the full 4.4 percentage-point observed gap.

A paired **length-only** diagnostic repeated the exact same first 32 IDs/seeds/prompt/model/threshold/steps at `gen_length=1024`. The 30 samples that already exited by EOS at cap 512 had **byte-identical postprocessed outputs** at cap 1024. Only IDs 2 and 13 differed: both previously hit the 512-token cap, and both now terminated at EOS with the correct parsed answer. Accuracy moved from 29/32 to **31/32 = 96.875%** (Wilson 95% CI 84.26–99.45%), with 32 EOS, zero caps, zero remaining MASK and zero empty outputs. Thus generation length and the fallback parser jointly account for those specific failures without a new decoder or threshold policy. This justified repeating the first 128 IDs at cap 1024 before freezing the full-test setting.

The cap-1024 parser audit reused the **47 byte-identical** outputs among the first 50 IDs and manually rechecked the only three changed cases (IDs 2, 13, 41). Raw parser and human-visible scores both became **47/50 = 94%**: two true model errors and one unfinished cap-1024 case. The 50-row audit is `artifacts/reproduction/parser_validation_cap1024.csv` with decisions in `parser_review_first50_cap1024.csv`. ID 41 still terminates mid-calculation at 1024 tokens after 755 actual forwards; it is explicitly `TRUNCATED`, not a demonstrated model arithmetic error. A longer cap must be checked before final full-test setting.

The same 1024-token setting then completed all first 128 IDs: **117/128 = 91.406%** raw parser accuracy (Wilson 95% CI **85.27–95.13%**), with 125 EOS, three length caps, zero MASK/empty outputs, mean/median NFE **100.26/73** and mean/median generation length **191.90/155** tokens. IDs 41, 115 and 119 still met the cap; they are retained as termination/format diagnostics, not silently credited as model errors. In view of these tails, representative 2048-token fixed-length probes and the official dInfer Mini `gen_len=2048` path were checked before freezing the full-test setting. The completed Stage-B machine summary is `artifacts/reproduction/gsm8k_stage128_cap1024_summary.json`.

The first cap-2048 probe (ID 41) completed without GPU OOM but still hit the length cap after **1,411** forwards. The fallback last-number parser happened to extract the correct `200`, yet the visible output repeatedly revisits contradictory interpretations and never settles on a final answer. This is classified as a **parser false positive / unfinished-format case**, not a demonstrated quality recovery, and is excluded from the strict human-visible score even though the raw scorer says correct. The second fixed cap-2048 probe (ID 115) also completed without OOM, but hit the cap after **1,410** forwards and gave the wrong `10` instead of `90`; the output remained in a self-questioning loop. Physical H100s 4–7 ran independent single-GPU workers; there is no EP/TP performance claim. Raw parser score, EOS/cap counts and human-reviewed finished answers are reported below.

## Full GSM8K test (1,319 fixed IDs)

All IDs 0–1318 were generated exactly once under the frozen cap-2048 official Mini path. The raw number parser scored **1,211/1,319 = 91.81%** (Wilson 95% CI **90.21–93.17%**). Generation ended by EOS for **1,292**, at the length cap for **27**, with **zero remaining MASK or empty outputs**. Mean/median NFE was **109.28/70**; mean/median generated length was **214.87/155** tokens. Six capped outputs happen to have a parser-extracted number matching the gold answer, but this alone does not prove a stable final answer. The automatic termination-aware triage calls **1,208/1,319** correct; it is a conservative diagnostic, **not** a manually adjudicated alternate benchmark score. Two terminated cases are exact numeric-equivalence parser false negatives (`42.00` versus `42`, `9.00` versus `9`). The mandatory manually reviewed first 50 IDs have **47/50** stable, human-visible correct answers versus **48/50** raw parser matches; the extra raw match is unfinished capped ID 41. The 27 length-cap cases and all parser-suspicious cases are retained in `artifacts/reproduction/gsm8k_full2048_parser_triage.csv`, while the complete prompts/outputs/NFE/termination and exact scoring are in `gsm8k_samples.jsonl` and `gsm8k_full2048_summary.json`.

The official Mini card's **94.24%** is **2.43 percentage points higher** than our raw score and lies just above its finite-sample Wilson upper bound. This is a **meaningful residual protocol/score gap**, not the previous catastrophic 10.92% failure. Exact published decoding, RNG, evaluation parser and prompting details are not all identical to this pinned HF/dInfer-YAML hybrid anchor; source inspection in particular shows nominal `temperature=0` uses multinomial sampling in the HF path, while dInfer's Mini evaluation shell uses a different decoder and threshold. No threshold adjustment or optimization was used to close the gap.

## HumanEval secondary validation

The first eight official HumanEval test IDs were generated with the same pinned HF Mini model and a 512-token cap. An initial **3/8** executable score was traced to an **evaluator bug**: when the model returned a complete function in a Markdown code fence, our scorer replaced the original prompt but dropped its import prelude, causing five false `NameError: List is not defined` failures. The evaluator now preserves the original prelude without duplicating the unfinished target function; a regression test verifies that this fixes the annotation import while the generated solution remains unmodified. Re-running the *same captured outputs* gives **7/8 pass@1**. The remaining failure is the model's actual `_deviations` undefined-variable error, not a sandbox/import failure. The sandbox executes generated code in isolated user/mount/network/PID namespaces with no host home or network, and its correctness/isolation tests pass.

Two of the eight 512-cap outputs were length-capped despite passing their tests. A paired length-only repeat at cap 1024 made those two terminate at EOS; the other six outputs were byte-identical and the executable score remained **7/8**. We therefore froze cap 1024 for the remaining 156 HumanEval IDs. After full GSM8K, another user's process occupied physical GPUs 0, 4, 6 and 7; it was not terminated. HumanEval generation consequently used only free physical GPU5, and no latency claim is made.

All **164** HumanEval problems were generated and executed. A second evaluator audit found that one response contained an illustrative code fence before a later fence with the actual entry-point implementation; selecting the first fence caused a false failure. The scorer now selects the last fenced candidate that defines the required entry point, with a regression test covering this case. Rescoring the unchanged captured generations gives **143/164 = 87.20% pass@1** (Wilson 95% CI **81.22–91.47%**). Mean/median NFE is **189.01/146**. There are **9 syntax failures**, **0 sandbox failures**, **18 length-cap terminations** and **0 empty outputs**; the 21 executable failures comprise 11 `AssertionError`, 9 syntax errors and 1 `TypeError`. The official Mini card's 86.59% is inside our interval and differs by only **+0.61 percentage points**. Complete generated outputs, executable outcomes and counters are stored in `artifacts/reproduction/humaneval_samples.jsonl` and `humaneval_full164_summary.json`.

## Reference comparability

The [official Mini card](https://huggingface.co/inclusionAI/LLaDA2.0-mini) reports GSM8K 94.24 and HumanEval 86.59. These numbers are not automatically matched: exact few-shot/prompt, length, decoding, sample/evaluator and executable-code protocol must be verified before interpreting a gap. Our source-level anchor is the card's own generation example and the official Mini GSM8K YAML, with exact revision and all sample records preserved.

|---|---|---:|---:|---:|---:|---|
| Official model card | LLaDA2.0-mini | 94.24% | 86.59% | 0.95 reported in paper | 32 | Published protocol is not fully score-matched to the public HF path |

The GSM8K difference is **-2.43 percentage points** and the official value is just above our Wilson interval. This residual is material and must accompany reuse of the score, but it is not an unexplained catastrophic gap: the public HF path samples even at nominal temperature zero, whereas the official dInfer shell uses another decoder and threshold; exact published RNG, parser and executable protocol are not fully specified. HumanEval is statistically and numerically consistent with the card. This PoC establishes a trustworthy, exactly pinned **quality baseline for this recorded protocol**, not a claim of bit-identical reproduction of an unpublished benchmark harness and not a latency baseline.

## Decision

**`REPRODUCED`**

The generation is structurally valid, all required benchmark cohorts are complete, the parser/evaluator has been manually and regression-tested, and there is no remaining catastrophic unexplained quality gap. The older 10.92%/7.93% artifacts are not valid Mini baselines: they used Flash 100B, a short effective generation budget, a different decoder/prompt/threshold and different evaluators. In the old GSM8K cohort, **96.2%** of outputs ended within two tokens of their effective generation cap, directly demonstrating a severe termination confound. Because several boundaries changed simultaneously, no single factor is claimed as the sole cause.

Answers to the required final questions:

1. **Why was the old GSM8K score 10.92%?** It came from an incompatible Flash-100B/custom-runtime protocol with an acutely short effective generation budget and a truncation-sensitive parser, not from the pinned Mini reference path. The evidence identifies these as major confounds but does not isolate a sole cause.
2. **What is the reproduced quality?** GSM8K is **1,211/1,319 = 91.81%**; HumanEval is **143/164 = 87.20% pass@1**.
3. **How far is it from the reference?** GSM8K is **2.43pp lower** than 94.24%; HumanEval is **0.61pp higher** than 86.59%.
4. **Is the difference explainable?** Yes at the protocol level: public HF sampling semantics, the separate dInfer decoder/threshold, generation limits, prompts and scorer details are not exactly identical. The remaining GSM8K delta is reported rather than tuned away.
5. **Can this generation/evaluator be trusted as a research baseline?** Yes for quality experiments that preserve the pinned checkpoint, prompt, generation wrapper, seed and scorers. It is not a clean latency baseline because evaluation used independent workers and was not timed under controlled occupancy.
6. **Final verdict:** **`REPRODUCED`**.

The recommended next step is a separately authorized Phase-2 true-EP validation/profile using this exact quality boundary. It was **not started** here. No threshold sweep, EP optimization, controller, kernel experiment or utilization burn was run as part of finalization.
