# C02: KV-stationary remote MLP pool

## 1. Identity

Revision 1. Search family: B. Initial category: recurrence hybrid.

## 2. Mechanism

Keep attention state on its owner and send ready normalized activations to shared MLP workers.

## 3. Relevant model property

The audited Base checkpoints share physical weights across four passes but retain depth-indexed state.
See `reports/ouro_semantics_audit.md` for pinned source locations.

## 4. Target scope

Both Base sizes, fixed R4, and the unchanged adaptive gate are scope targets, not demonstrated gains.
Primary C is 1/2/4/8. Contexts are 1K/4K/8K. P2/P4 require physical tests. P8 remains projected.

## 5. Baseline and saved cost

Compare mode-matched native 1GPU and the strongest correct same-P conventional baseline.
The hypothesized saving is: Possible larger MLP batches without moving historical KV.

## 6. Operation sequence

Local attention and MLP -> local attention -> remote MLP round trip -> exact residual and norm.

## 7. Legal DAG and ownership

Each task must identify request, token/chunk, recurrent depth, physical layer, layout, and version.
Weights are immutable. Historical KV belongs to its matching committed request/depth/layer prefix.
Current KV remains private until its complete input and commit rule pass.
The generic validator is `scripts/verify_dag.py`. This card is not a completed candidate-specific executable DAG.

## 8. Source of concurrency

Independent state owners can supply different ready requests or depths to one physical MLP batch.

## 9. Exactness and quality

Numerically reordered exact graph.
Quality remains NOT_RUN for a new mechanism.
Use the frozen free-running calibration and held-out protocol before a quality-preservation claim.

## 10. State and memory

Charge unique and replicated weights, full required depth KV, current activations, graph buffers, and candidate scratch separately.
For H=2048, full BF16 KV is 786432 bytes/token at L24/R4 and 1572864 at L48/R4.
These are structural capacities, not measured HBM traffic.

## 11. Messages and topology

Only physical 4/5/6/7 are eligible for P2/P4.
Every message needs a producer, consumer, byte count, and completion dependency.
No zero-cost KV movement or unsupported eight-GPU result is permitted.

## 12. Added costs and critical path

Use a resource-constrained path. Do not add overlapping intervals or replace serial work with a maximum without ready inputs.

## Evidence update 1

The measured one-owner/one-worker layout keeps attention and its historical KV on the source.
It sends a complete post-attention MLP input to a remote full-weight worker.
The source waits for the complete returned output before its following normalization and layer.

| State | Owner and lifetime | Required transfer |
|---|---|---|
| Historical depth/layer KV | Attention owner, committed request prefix | None for this layout |
| Current attention state and residual | Attention owner, current exact version | None for this layout |
| MLP weights | Remote worker, immutable checkpoint | Resident before the test |
| MLP input | Source, after required normalization | 4096 bytes per BF16 row |
| MLP output | Worker, after down projection | 4096 bytes per BF16 row |

The P2/P4 graph-captured test includes both directions and the complete dense MLP.
The returned source output matches the local component bitwise on the tested inputs.
The remote path is slower at every tested row count for both checkpoints.
This prunes that layout for an isolated request with unchanged serial attention work.
It does not reject every pooled or hybrid A/FFN architecture.

KernelFlume and AFD are direct generic ownership controls.
The useful pooled frontier and the strongest same-P baseline remain necessary for a different layout.
Current status: `NO_NET_HEADROOM` in the tested one-owner layout, with `GENERIC_ONLY` novelty as presently defined.
